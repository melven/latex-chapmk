# S15: first-page material when the document starts with an \include

**Question.** The record comparison of SyncTeX files (§3.3 item 4, normalised records) found an
extra empty record at the top of a chapter's first page after an incremental build, in
`test_open_action_when_the_document_starts_with_an_include`: the document starts with
`\include{a}`, and a run compiled only `c`. Where does it come from, and does it change the
PDF?

**Setup.** TeX Live 2026 (pdfTeX 1.40.29), dev image. `tests/corpus/minimal/S15-first-page/`
(`report`, xcolor, hyperref, bookmark, three `\include`s without text before them); `run.sh`
prints the first records of each page for a plain full build and for `\includeonly{c}`, then
builds with chapmk (cold, edit of `c`) and counts the records per page against `check`'s
reference.

## Results

- With hyperref, the first page of a full build starts with a zero-size record
  (`h…:4736286,4736286:0,0,0`); without hyperref it does not. With plain pdflatex and
  `\includeonly{c}`, the same record is at the top of `c`'s first page: it is not caused by
  chapmk, but by what goes onto the first page TeX ships.
- That material: the nodes on the main vertical list at `\begin{document}` (`\showlists`:
  an empty `\write`, hyperref's `\pdfdest name{Doc-Start}`, with xcolor its
  `\pdfcolorstack 0 push`, which S13 puts back at the split point) and LaTeX's
  `shipout/firstpage` hook (used by hyperref), which LaTeX adds to its first `\shipout`.
- In a chapmk run that excludes the first unit, all of it landed on the run's first page, a
  later page of the document: an extra SyncTeX record, a second `Doc-Start` destination (the
  merge keeps the one on the lowest page, §6.11) and, with xcolor, an extra colour stack
  operation in that page's content stream. Pixels and text were identical, so §3.3 with
  sampled SyncTeX queries did not notice.
- First attempt: ship the main vertical list's nodes on an extra page with the primitive
  `\shipout` (as picture export does). The `Doc-Start` node moved, but the record stayed: the
  `shipout/firstpage` material still went onto the next LaTeX `\shipout`.
- `\RawShipout` (LaTeX 2020-10) runs the first-page hook and counts the page in the shipout
  counter, but not the `shipout/before` hooks, so chapmk writes no page record for it and
  the merges skip it. With it, the records per page equal the reference
  (`[55, 41, 54, 41, 53, 41]` with xcolor, `[48, 34, 47, 34, 46, 34]` without).

## Consequence

`chapmk.sty`: before the first excluded unit's checkpoint (`\chapmk@excluded@begin`), if the
run has shipped nothing yet, a local output routine (as `\chapmk@capturemvl`, S13) takes the
pending nodes off the main vertical list and ships them with `\RawShipout` on an extra page
(`\chapmk@firstpage`). Their effects (colour stack) still hold for the run's pages. Design
§6.5; scenario test `test_first_page_material_when_the_first_unit_is_excluded`.

## Follow-up: order relative to the entry record

The extra page was first shipped before the unit's entry record (`\chapmk@unit@begin`).
Deferred writes before the first `\include` (`\addtocontents{toc}{...}`, babel's
`\babel@aux` from `\selectlanguage` or `\begin{document}`) are on that page; they reached the
main aux between `\@input{<unit>.aux}` and the unit's entry record, so the list files had them
inside the unit's section (`\chapmk@lmark{U1}` ... `{/U1}`). A run that compiles the unit
writes the entry record at `include/before`, before any of its pages ships: there they come
after `{/U1}`. The self-check of kept sections (§6.7) then failed in every build that excluded
the first unit (fallback to full mode; the journal left behind made the next build cold).
Seen in a real thesis (babel, title page as the first `\include`); reproduced by
`test_list_writes_before_the_first_include` (book, a one-page first unit, `\addtocontents`
or babel's `\selectlanguage` before it). Consequence: `\chapmk@excluded@begin` ships the extra
page after `\chapmk@unit@begin`.
