# S12 — picture cache (TikZ external under fastinc)

**Question.** Can fastinc reuse typeset TikZ pictures across incremental runs (PLAN §6.17) and still meet §3.3? What does it cost and save, and which pictures must stay inline?

**Setup.** TeX Live 2026, dev image. Reproducer: `tests/corpus/minimal/S12-picture-cache/`.
- `run.sh OUT [SRC]` runs the following steps:
  1. reference: 3 inline passes;
  2. fill: one cache-mode pass with an empty cache, using the reference aux files;
  3. `split.py`: extracts the exported pictures;
  4. use: one pass with the cache, once with export and once without (`use2`);
  5. `compare.py`: §3.3 items 1–4 with `fastinc.check`.
- `kinds.sh OUT`: one generated document per picture kind (`gen_stress.py`: 2 units, each picture in different positions: figure, inline, baseline, itemize, table, center). `pages.py` gives the per-page differences.
- Prototype `s12probe.sty`:
  - TikZ `external` in mode *graphics if exists*, names `fig/<unit>-<n>`;
  - a missing picture is typeset inline, and a copy of its final box is shipped as an extra page with the primitive `\shipout` (no LaTeX hooks). The copy goes in the same run, so no extra jobs are needed;
  - log record: name, PDF page, box dimensions, and the `\count` registers changed by the picture;
  - aux lines written while the copy is shipped are fenced;
  - embedding: `\pgfimage` at natural size (scale 1), box dimensions set to the inline values. The `.dpth` file carries the depth, the dimensions and the register deltas.
- `split.py` rules: a picture is not cached if its page has annotations, is a destination target, or wrote aux lines, or if it changes registers other than the pgf picture id. `remember picture` pictures are never exported.

**Results**

1. **Mechanics work.**
   - The fill run with extra pages is identical to the reference after the extra pages are dropped (§3.3 items 1–3). It costs no measurable time (3.45 s vs 3.4 s).
   - Every picture of a unit becomes a cache file in one run.
2. **Time.**

   | Document | Inline pass | Cached pass |
   |---|---|---|
   | small document | 3.4 s | 1.15 s |
   | stress document (41 pictures, 5 not cached) | 3.3 s | 2.0 s |

3. **§3.3 equality.**
   - **Small document:** identical in all items (raster, text, labels, outline, links, SyncTeX at 40 samples per unit). This needed:
     - natural-size embedding: scaling to the exact box size gave 33 differing pixels;
     - `\spacefactor` handling.
   - **Per picture kind** (cached pass vs inline reference, 150 dpi):

     | Kind | Raster | `-layout` text |
     |---|---|---|
     | plot, graph, scaled, image, shading, opacity | 12–250 pixels per page, single anti-aliasing edge pixels (max delta 9–158 of 255) | same |
     | pattern | 23 000–42 000 pixels per page: the tiling phase moves (pattern space of a form XObject) | same |
     | pgfplots | identical | same |

     pgfplots is identical only because all 18 axes stayed inline (register changes, item 4); only 3 small pictures were cached.
   - **Mixed stress document:** one page also differs in `-layout` text (column spacing).
   - **Cause:**
     - pdfTeX rounds coordinates to `\pdfdecimaldigits=3` bp;
     - inline: round(X + dx); embedded: round(X) + round(dx), i.e. up to 0.001 bp apart.
     - This is inherent to embedding. Raising the digits would only shrink it (not measured), and it would change the reference build.
4. **Side effects that are lost when a picture is embedded.** Each was detected and kept inline in the prototype:
   - links and anchors (pdfTeX drops annotations of included pages; every `\ref` with hyperref is a link);
   - `remember picture` (positions are written at shipout; without the picture the overlay arrow moved);
   - aux writes (`\label` in a node);
   - register changes:
     - the pgf picture id must be advanced: without it, `remember picture` ids shift and the overlay moved;
     - `\tikz@fig@count` +2 for each pgfplots picture;
     - the first pgfplots picture initialises several registers.
5. **Validity (analysis).**
   - TikZ external checks only the picture code (md5).
   - The output also depends on:
     - state: `\thepage`, `\thefigure`, `\ref` values, `\linewidth`, font;
     - the glue (`\appendix` changes `\thefigure`) and the format.
   - A sound key: md5(code) + format stamp + glue hash + counter vector at picture start + `\linewidth`/font + the values of the labels and citations the picture uses.
   - With the counter vector in the key, the recorded register changes can be replayed exactly. Then pgfplots (`\tikz@fig@count`) becomes cacheable.
   - In the typo case all keys stay the same. Inserting a picture or an equation invalidates the later pictures of the unit.

6. **Part 2: reference with the user's externalize** (`run_ext.sh OUT [SRC]`).
   - Reference: the document with a real `\tikzexternalize[prefix=figref/]`, shell escape, figure jobs, 3 passes.
   - Compared with: fastinc-style figures (exported in the same run) embedded by TikZ external's own code: `\pgfimage` at natural size, depth from `.dpth`, no register replay, every picture embedded.
   - Results:

     | Document | Externalize cold pass (figure jobs) | Fill pass | Cached pass | §3.3 |
     |---|---|---|---|---|
     | per kind (8 kinds, 21 pictures each) | 28–45 s | 1.4–5.3 s | 1.4–1.6 s | identical, all items incl. SyncTeX |
     | mixed (41 pictures) | 60 s | 3.3 s | 1.5 s | identical |

   - Identical for patterns as well: both sides embed form XObjects, so rounding and pattern phase are the same.
   - The pictures produced in the same run are equivalent to externalize's figure jobs, without shell escape.

**Consequences for the plan** (decision point, CLAUDE.md)
- **Without the user's externalize**, an embedded picture cache cannot meet §3.3 item 1 (pixel identity): anti-aliasing edge pixels differ and tiling patterns shift (items 3 and 4). Pictures stay inline there.
- **Decision (user):** the result must be identical to TikZ externalize. Consequences:
  - fastinc honours an externalize that the user sets up in the document; only its settings are altered (prefix and names in the build directory, mode, no system calls). The reference (`--full`) uses the same altered settings.
  - Semantics follow externalize:
    - `\tikzexternaldisable`/`\tikzexternalenable` and `\tikzsetnextfilename` are honoured;
    - every other picture is embedded, also with links (lost as with externalize);
    - no register replay.
  - Figures are exported in the same run, without shell escape. A unit with new or changed figures needs one more pass to embed them.
  - Validity key: as in item 5 (stricter than externalize's md5), so the result equals a fresh externalized build.
  - Without `\tikzexternalize` in the document, pictures stay inline (as now).
